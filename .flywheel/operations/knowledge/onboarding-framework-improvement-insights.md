# Onboarding Framework Improvement Insights

## Purpose

This document captures framework-level lessons discovered while onboarding `Infoconex/ai-flywheel-cli-python`. It is intended for later use when improving the AI Flywheel framework. These are observations and recommendations only; no framework changes are made by this document.

## Summary

The onboarding process worked, but it exposed several places where the framework should provide stronger contracts for repositories that build or distribute Flywheel tooling. The most important improvements are:

1. Clarify that onboarding may resolve implementation-policy decisions without performing implementation.
2. Define how generated artifacts must be executed and validated after creation.
3. Support human delegation of recommended onboarding decisions.
4. Separate recommendation origin from human approval in provenance.
5. Make answer, evidence, and configuration persistence atomic and recoverable.
6. Introduce a dedicated implementation decision register.
7. Expand conditional onboarding for tool-producing repositories.
8. Define a practical stopping rule for onboarding.

## 1. Clarify onboarding as decision discovery

The framework currently distinguishes onboarding from application work and later tool implementation. That boundary is correct, but it should be more explicit for repositories that implement Flywheel tooling.

Recommended contract:

> When the target repository implements or distributes Flywheel tooling, onboarding must resolve the operating, packaging, safety, upgrade, execution, and validation policies required to create implementation goals. It must not implement those decisions during onboarding.

This distinction prevents confusion between:

- describing future implementation requirements
- creating implementation goals
- generating code or scaffolding
- executing generated code as validation

## 2. Add a generated-artifact execution contract

The framework should distinguish among:

- configuration describing future implementation
- code or scaffolding generated by a later goal
- execution required to prove generated content works

Recommended model:

```yaml
generated_artifacts:
  must_be_executable: true
  post_creation_validation_required: true
  completion_command: python -m tools validate
```

The framework should require the goal that creates generated artifacts to execute the configured validation command before completion. Merely creating files is not sufficient evidence that generated scaffolding works.

## 3. Support recommended-default delegation

During onboarding, the human authorized the operator to select all remaining recommended answers. The framework should model this explicitly rather than recording every later choice as though the human answered each question directly.

Recommended model:

```yaml
decision_delegation:
  scope: remaining-onboarding-decisions
  authority: recommend-and-select
  constraints:
    - do not cross existing approval boundaries
    - do not enable hosted services
    - persist rationale and provenance
    - surface high-impact or irreversible decisions
```

Delegation should not authorize actions outside established governance. It should apply only to the decision scope granted by the human.

## 4. Expand provenance semantics

The existing provenance concepts do not clearly distinguish these two facts:

- the operator recommended a value
- the human approved a policy allowing the operator to select it

A cleaner model separates origin from approval:

```yaml
origin: recommended
approval:
  method: delegated
  status: approved
  evidence_ref: EVIDENCE-...
```

Possible origin values could include:

- discovered
- provided
- inferred
- defaulted
- recommended

Approval should be represented independently, such as:

- not-required
- pending
- explicitly-approved
- delegated-approved
- rejected
- deferred

This avoids overloading one field with both source and authority.

## 5. Define atomic answer and evidence persistence

The onboarding process created evidence and then updated configuration. This exposed a risk of evidence-number drift, missing references, or interrupted transitions.

The framework should define a deterministic persistence transaction:

1. Read the evidence index or sequence source.
2. Reserve the next evidence identifier atomically.
3. Write the evidence record.
4. Update every affected configuration or decision record.
5. Validate references in both directions.
6. Mark the transition complete only after all writes validate.
7. Recover or roll back incomplete transitions deterministically.

The framework should also define how duplicate identifiers, missing identifiers, and sequence gaps are handled.

## 6. Add an implementation decision register

`flywheel-context.yaml` became a mixture of:

- resolved configuration
- operational policies
- dependency selections
- implementation decisions
- rationale and explanatory notes

A dedicated register would preserve decision history without overloading configuration.

Recommended path:

```text
.flywheel/operating-model/config/implementation-decisions.yaml
```

Recommended shape:

```yaml
- id: CLI-FRAMEWORK-001
  category: implementation
  status: confirmed
  statement: Use Typer as a thin CLI adapter.
  rationale: >-
    Typer provides typed command definitions and generated help while allowing
    application behavior to remain independent of the CLI framework.
  evidence_ref: EVIDENCE-020
  consequences:
    - CLI handlers remain thin.
    - Core behavior must be independently testable.
```

The context file should hold the resolved values. The decision register should hold why and under what authority they were selected.

## 7. Expand onboarding for tool-producing repositories

The current broad questions about execution location, portability, and technology preference are insufficient when the repository builds installers, generators, validators, or lifecycle tools.

The interview should conditionally add questions in these areas:

### Distribution and installation

- release source
- version selection
- checksum verification
- installer and package-manager behavior
- offline expectations
- existing-installation behavior

### Safety and recovery

- approval before writes
- transactional installation
- rollback behavior
- archive extraction security
- path traversal prevention
- network timeout and retry policy

### Upgrade behavior

- framework-owned file identification
- per-file installation checksums
- local modification detection
- conflict handling
- compatibility and migrations

### Concurrency and runtime state

- repository-level operation locking
- stale-lock recovery
- temporary staging location
- version-control exclusions

### Interface contracts

- human-readable output
- structured output such as `--json`
- stable exit codes
- diagnostics and secret redaction

### Validation and release discipline

- unit tests
- integration tests
- fixture-based end-to-end tests
- generated-artifact execution
- local versus hosted validation
- release archives, checksums, and release notes

These questions should only appear when repository evidence or declared purpose identifies the project as tooling, installer, generator, framework, or distribution infrastructure.

## 8. Define when onboarding stops

The framework currently requires material unknowns to be resolved or deferred, but this can lead to an open-ended design interview.

Recommended stopping rule:

> Stop onboarding when enough confirmed context and decisions exist to define coherent implementation goals with testable acceptance criteria. Do not continue selecting low-level design details that can safely be decided and validated within an implementation goal.

Onboarding should continue when a missing decision would materially change:

- goal boundaries
- approval requirements
- architecture direction
- installation or upgrade safety
- evidence requirements
- compatibility expectations

Onboarding should stop when remaining choices are local implementation details that can be reversed and tested within a goal.

## Recommended framework change set

Before implementing the Python CLI, the highest-value framework updates are:

1. Recommended-default delegation support
2. Generated-artifact execution contract
3. Conditional interview extension for tool-producing repositories
4. Dedicated implementation decision register
5. Atomic answer and evidence persistence rules
6. Explicit onboarding stopping rule

## What should remain repository-specific

The following choices discovered during this onboarding should not become universal framework defaults:

- Python 3.11+
- Typer
- pytest
- Ruff
- mypy
- `src/` layout
- 80 percent coverage threshold
- `python -m tools`
- GitHub Release archives as the distribution source
- `uv`, `pipx`, and managed virtual-environment installer behavior

These belong in the Python CLI repository's operating context. The framework should define how such decisions are discovered, approved, persisted, and validated without prescribing the values.

## Intended follow-up

Use this document later to create a focused framework mission or goal set. Framework changes should be made on a new framework branch, validated independently, and not merged without human approval.
